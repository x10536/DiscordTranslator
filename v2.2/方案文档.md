# Discord 实时翻译软件 - 最终技术方案文档

> 本文档为完整技术方案，供开发参考。可直接交给 AI 或开发者阅读执行。

---

## 一、项目背景

### 用户痛点
用户看不懂英文，但需要浏览 Discord 英文社区的频道消息和聊天记录。英文对用户不友好，需要一个能实时翻译 Discord 聊天内容的工具。

### 目标
做一个 Windows 翻译软件，用户下载后即可使用，鼠标悬停在 Discord 英文消息上自动翻译，以中文气泡形式展示在原文上方。

---

## 二、技术方案选型过程

### 方案对比

| 方案 | 文字获取方式 | 准确率 | 速度 | 开发周期 | 稳定性 | 用户门槛 |
|------|------------|--------|------|---------|--------|---------|
| EXE + OCR | 截图+OCR识别 | 90-95% | 0.8-1.5秒 | 5-7天 | 中 | 下载exe |
| EXE + CDP + OCR | 调试端口读DOM+OCR兜底 | 95-100% | 0.3-1.5秒 | 5-7天 | 中 | 下载exe |
| BetterDiscord插件 | 直接读DOM | 100% | 0.2-0.4秒 | 3-4天 | 低 | 需装BD |
| **Chrome插件注入桌面客户端** | **直接读DOM** | **100%** | **0.2-0.5秒** | **2-3天** | **高** | **换快捷方式启动** |

### 最终选择：Chrome 插件 + 注入 Discord 桌面客户端

**核心原理**：Discord 桌面客户端是 Electron 应用，内核就是 Chromium 浏览器。Chrome 扩展可以通过 `--load-extension` 参数直接注入到 Discord 桌面客户端中运行，直接操作 DOM 获取文字，无需 OCR。

## 四、核心功能详细设计

### 4.1 鼠标悬停翻译

**流程**：

```
鼠标悬停在 Discord 消息上
  │
  ▼
content.js 监听到 mouseover 事件
  │
  ▼
从 DOM 中直接获取消息元素的文字内容（100%准确）
  │
  ▼
判断文字是否为英文（正则判断/Unicode范围判断）
  │ 非英文 → 不处理
  ▼ 英文
防抖等待 300ms（鼠标在此期间移走则取消）
  │
  ▼
查询本地缓存（Map对象，key=英文原文）
  │ 命中 → 直接显示气泡
  ▼ 未命中
调用 DeepSeek API 翻译
  │
  ▼
将结果存入缓存
  │
  ▼
在英文消息上方插入气泡 div，显示中文翻译
```

**关键技术点**：
- Discord 消息元素的选择器：需要通过实际 DOM 分析确定，通常消息内容在 `div[id^="message-content-"]` 或类似元素中
- 防抖：鼠标停下 300ms 不动才触发，快速滚动时不触发
- 英文判断：通过 Unicode 范围判断字符是否主要为拉丁字母

### 4.2 翻译气泡 UI

**样式要求**：
- 背景：黑色半透明（`rgba(0, 0, 0, 0.75)`）
- 文字：白色（`#ffffff`）
- 字体：系统中文字体（微软雅黑/PingFang SC）
- 圆角：8px
- 内边距：10px 14px
- 最大宽度：400px（过长自动换行）
- 阴影：`0 2px 8px rgba(0,0,0,0.3)`
- 小三角箭头：指向原消息

**定位逻辑**：
- 气泡 `position: absolute`，相对于英文消息元素定位
- 显示在消息上方（`bottom: 100%` + `margin-bottom: 8px`）
- 如果上方空间不足（消息在顶部），自动翻转到下方
- `z-index: 99999` 确保在最上层
- `pointer-events: none` 气泡不拦截鼠标事件（鼠标可以"穿过"气泡）

**显示/隐藏**：
- `mouseover` 触发显示
- `mouseout` 触发隐藏，加 100ms 延迟消失（防止鼠标在两条消息间移动时闪烁）
- 隐藏动画：`opacity: 1 → 0`，150ms 过渡

### 4.3 翻译缓存

**方案**：内存缓存（Map 对象）

```
缓存结构：
cacheMap = {
  "Hey guys, anyone playing tonight?": "嘿伙计们，今晚有人玩吗？",
  "That's awesome!": "太棒了！",
  ...
}
```

**策略**：
- 相同英文句子只请求一次 API
- 缓存上限 1000 条（LRU 淘汰最久未使用的）
- 页面刷新后缓存重建（Discord 切换频道时缓存不清空，因为插件一直在运行）

### 4.4 翻译 API 对接

**DeepSeek API**：

```
接口：https://api.deepseek.com/v1/chat/completions
方法：POST
Headers:
  Authorization: Bearer {API_KEY}
  Content-Type: application/json
Body:
{
  "model": "deepseek-chat",
  "messages": [
    {"role": "system", "content": "你是翻译助手，将英文翻译成自然流畅的中文。只返回翻译结果，不要加任何解释。"},
    {"role": "user", "content": "翻译这段英文：{原文}"}
  ],
  "temperature": 0.3,
  "max_tokens": 500
}
```

**注意**：
- API Key 存储在 `chrome.storage.local` 中
- 请求超时设置 10 秒
- 超时/失败时气泡显示"翻译失败，请检查网络或API Key"
- 后续可切换其他模型（GPT/Claude等），只需改 API 地址和 Key

## 六、启动器设计

### 6.1 功能

用户双击启动器，自动用带插件参数的方式启动 Discord。

### 6.2 实现（Python 打包为 exe）

```python
# launcher.py 核心逻辑伪代码
import subprocess
import os
import sys

# 获取插件目录（相对于启动器所在目录）
plugin_dir = os.path.join(os.path.dirname(sys.argv[0]), "extension")

# Discord 安装路径（常见路径）
discord_paths = [
    os.path.join(os.environ.get("LOCALAPPDATA", ""), "Discord", "Update.exe"),
    os.path.join(os.environ.get("LOCALAPPDATA", ""), "Discord", "app-*", "Discord.exe"),
]

# 启动 Discord 并加载插件
cmd = [discord_path, "--processStart", "Discord.exe",
       "--process-start-args", f"--load-extension={plugin_dir}"]
subprocess.Popen(cmd)
```

## 九、关键技术难点与解决方案

### 难点1：Discord 消息元素选择器

Discord 的 DOM 结构会随版本更新变化，消息元素的选择器可能失效。

**解决方案**：
- 不依赖单一选择器，使用多级 fallback 策略
- 优先用稳定的属性（如 `data-list-item-id`、`role="listitem"`）
- 监听 `mouseover` 事件时向上查找最近的合法消息容器
- 提供 CSS class 注入作为备用（给消息元素打标记）

### 难点2：Discord SPA 路由切换

Discord 是单页应用，切换频道时不会刷新页面，新消息是动态加载的。

**解决方案**：
- 使用 `MutationObserver` 监听 DOM 变化
- 新消息节点出现时自动绑定悬停事件
- 不依赖页面加载事件，而是持续监听 DOM 变化

### 难点3：气泡定位在动态滚动内容中

Discord 聊天区域会滚动，气泡需要跟随消息元素。

**解决方案**：
- 气泡用 `position: absolute` 相对于消息元素定位
- 随消息元素一起滚动（因为在同一滚动容器内）
- 不用 `position: fixed`（会脱离滚动流）

### 难点4：Discord 的 --load-extension 参数

Electron 应用加载扩展需要特定参数格式，且部分版本可能限制。

**解决方案**：
- 使用 `--load-extension=` 参数（注意路径不能有空格，或用引号包裹）
- 如果该参数不生效，改用 `--remote-debugging-port=9222` + 通过 CDP 协议注入脚本
- 启动器中自动检测并选择有效方式

## 十、API 对接详情

### DeepSeek API

```
接口地址：https://api.deepseek.com/v1/chat/completions
请求方式：POST
认证方式：Bearer Token

请求头：
  Authorization: Bearer {YOUR_API_KEY}
  Content-Type: application/json

请求体：
{
  "model": "deepseek-chat",
  "messages": [
    {
      "role": "system",
      "content": "你是翻译助手。将用户给出的英文翻译成自然流畅的简体中文。只返回翻译结果，不加任何解释、不加引号、不加前缀。"
    },
    {
      "role": "user",
      "content": "Hey guys, anyone playing tonight?"
    }
  ],
  "temperature": 0.3,
  "max_tokens": 500,
  "stream": false
}

响应体：
{
  "choices": [
    {
      "message": {
        "content": "嘿伙计们，今晚有人玩吗？"
      }
    }
  ]
}
```

### 错误处理

| HTTP 状态码 | 处理 |
|-------------|------|
| 200 | 正常返回翻译结果 |
| 401 | API Key 无效，气泡显示"API Key无效，请检查设置" |
| 429 | 请求过多，气泡显示"请求太频繁，稍后再试" |
| 500 | 服务器错误，气泡显示"翻译服务暂时不可用" |
| 超时(10s) | 气泡显示"翻译超时，请检查网络" |

# 【重要更新】v2.0 最终实施方案（CDP 注入）

> 上文所述的"Chrome 扩展注入"方案经实测**不可行**，已改为 **CDP 注入方案**并验证成功。
> 以下为最终实施的方案，请以本节为准。

## 一、为什么扩展方案失败

| 问题 | 原因 |
|------|------|
| **Electron 不完整支持 Chrome 扩展** | Discord 虽基于 Chromium，但 Electron 官方仅支持扩展 API 的一个子集（主要面向开发者工具）。通过 `--load-extension` 加载的普通扩展，其 `content_scripts` **不会执行**，因此悬浮球永远不出现 |
| **Discord 卡在更新界面** | Discord 的更新器（Rust/reqwest）**不读取系统代理**，直连 `updates.discord.com` 失败后无限重试，导致主界面无法加载 |

**实测证据**：
- 带 `--load-extension` 启动 Discord 后，通过 CDP 检查页面：`TranslateModule: undefined`、`dt-* 元素数: 0` → 确认 content script 未注入
- 更新器日志：`ConnectionReset` 循环重试

## 二、最终方案：CDP 注入

### 原理

```
launcher.exe
   │ ① 结束旧 Discord
   │ ② 用调试端口启动 Discord：
   │    Update.exe --processStart Discord.exe
   │      --process-start-args "--remote-debugging-port=9333 --remote-allow-origins=*"
   ▼
Discord 主界面正常加载（discord.com）
   │ ③ 轮询 http://127.0.0.1:9333/json/list 等待页面
   │ ④ WebSocket 连接 CDP
   ▼
注入 inject.js
   · Page.enable
   · Page.addScriptToEvaluateOnNewDocument（持久注入）
   · Runtime.evaluate（立即注入）
   ▼
悬浮球 + 气泡 + 翻译功能生效
```

### 关键技术点

| 要点 | 说明 |
|------|------|
| **必须加 `--remote-allow-origins=*`** | 否则 CDP WebSocket 握手返回 403 Forbidden |
| **必须清除代理环境变量** | 若环境中存在 `HTTP_PROXY`/`HTTPS_PROXY`（如指向错误代理），Discord 会走错代理导致卡在更新界面。启动前需 `del` 这些变量 |
| **必须通过 Update.exe 启动** | 直接运行 `app-xxx\Discord.exe` 会立即退出 |
| **访问本地 CDP 端口要禁用代理** | Python 用 `urllib.request.ProxyHandler({})`，否则请求被系统代理拦截返回 502 |
| **配置存储** | 注入脚本运行在页面上下文，用 `localStorage` 存配置（API Key / 延迟 / 透明度 / 悬浮球位置） |

### 交付文件

```

├── launcher.exe        # 启动器（PyInstaller 打包，内置 inject.js）
├── inject.js           # 翻译脚本（24KB，悬浮球+气泡+翻译+设置面板）
├── launcher.py         # 启动器源码
```

```bash

```

注意：`--add-data` 必须用**绝对路径**（相对路径会因 `--specpath` 改变基准目录而失败）。

# 【重要更新】v2.1 最终实施方案（CDP 注入 + 原生桥接）

> v2.0 注入成功、悬浮球和气泡都正常，但填入 API Key 后翻译报 **"Failed to fetch"**。
> 本节记录该问题的根因定位过程与最终解决方案，**这才是可用的最终版**。

## 一、问题现象与根因定位

### 现象

悬浮球正常、悬停能弹出气泡，但气泡内容始终是"Failed to fetch"。

### 定位过程（用 CDP 逐层排查）

**第 1 步：确认不是网络问题**

```
命令行直连 api.deepseek.com      -> HTTP 200 ✓（能正常拿到翻译结果）
页面内 fetch api.deepseek.com    -> TypeError: Failed to fetch ✗
页面内 fetch discord.com         -> HTTP 200 ✓
```

→ 网络通畅，问题出在页面内。

**第 2 步：确认不是隔离世界（isolated world）问题**

用 `Page.createIsolatedWorld` 建隔离世界再测，结果一样失败：

```
[1] 主世界 fetch 测试:
   {"deepseek":"ERR: TypeError | Failed to fetch","discord":"HTTP 200"}
[2] 创建隔离世界: contextId = 8
   隔离世界 fetch 测试:
   {"deepseek":"ERR: TypeError | Failed to fetch","discord":"HTTP 200"}
```

**第 3 步：捕获 CSP 违规事件，确认根因**

```js
document.addEventListener('securitypolicyviolation', h);
await fetch('https://api.deepseek.com/v1/chat/completions', {...});
```

结果：

```json
{
  "violations": [{
    "directive": "connect-src",
    "blocked": "https://api.deepseek.com/v1/chat/completions",
    "policy": "default-src 'self'; script-src 'self' 'unsafe-eval' 'unsafe-inline' ..."
  }],
  "fetchError": "TypeError: Failed to fetch"
}
```

**根因确认：Discord 页面设置了 CSP `connect-src`，禁止页面 JS 请求外部域名。**
这是浏览器的安全机制，**不是代码 bug，也不是网络问题**，页面内无论怎么写都绕不过去。

### 试过但无效的方案

| 方案 | 结果 |
|------|------|
| `Page.setBypassCSP({enabled:true})` | ✗ 对已加载的文档不生效（CSP 已在文档上生效，需重载才可能生效，且属实验性 API，不稳定） |
| 隔离世界（isolated world） | ✗ 一样受 CSP 限制 |
| 换 CORS 配置 / 换请求头 | ✗ 与 CORS 无关，是 CSP |

## 二、最终方案：CDP 原生绑定桥接（Native Binding Bridge）

**核心思路：既然页面里不能发请求，那就让页面"呼叫"外部程序来发。**

利用 CDP 的 `Runtime.addBinding` 在页面里注册一个**原生函数**（不是网络请求，因此不受 CSP 约束），
页面 JS 调用它 → launcher.exe 收到事件 → 由 Python 发起 HTTPS 请求 → 再把结果送回页面。

```
┌──────────────────────────────────────────────────────────┐
│  Discord 页面（受 CSP 限制）                              │
│                                                          │
│  鼠标悬停 → 读取 DOM 文字 → window.__dtNative(payload)    │
│                                    │                     │
└────────────────────────────────────┼─────────────────────┘
                                     │ ① 原生绑定调用（不走网络，CSP 管不到）
                                     ▼
┌──────────────────────────────────────────────────────────┐
│  launcher.exe（Python，无 CSP 限制）                      │
│                                                          │
│  收到 Runtime.bindingCalled 事件                          │
│      → urllib 请求 api.deepseek.com                       │
│      → 拿到中文译文                                        │
│      → Runtime.evaluate 调 window.__dtDispatch(id, result) │
└────────────────────────────────────┬─────────────────────┘
                                     │ ② 结果回传
                                     ▼
                         页面渲染黑色半透明气泡
```

### 关键代码

**Python 侧（launcher.py）**

```python
# 1. 注册原生函数（对所有上下文生效，页面刷新后依然可用）
send('Runtime.enable')
send('Runtime.addBinding', {'name': '__dtNative'})

# 2. 注入页面脚本
send('Page.addScriptToEvaluateOnNewDocument', {'source': js_code})
send('Runtime.evaluate', {'expression': js_code, 'returnByValue': True})

# 3. 主循环：监听页面发来的调用
while True:
    msg = self._read(1.0)
    if msg.get('method') == 'Runtime.bindingCalled':
        p = msg['params']                      # {name, payload, executionContextId}
        req = json.loads(p['payload'])         # {id, method, params}
        result = handle_translate(req['params'])
        # 4. 结果回传页面
        expr = 'window.__dtDispatch(%s,%s)' % (json.dumps(req['id']),
                                               json.dumps(json.dumps(result)))
        self.send('Runtime.evaluate', {'expression': expr, 'returnByValue': True})
```

**页面侧（inject.js）**

```js
window.__dtDispatch = function (id, payloadJson) {
  const p = pending[id];
  if (!p) return;
  delete pending[id];
  const data = JSON.parse(payloadJson);
  if (data.ok) p.resolve(data.result);
  else p.reject(new Error(data.error || '未知错误'));
};

function call(method, params, timeoutMs) {
  return new Promise(function (resolve, reject) {
    const id = 'r' + (++seq) + '_' + Date.now();
    pending[id] = { resolve, reject };
    window.__dtNative(JSON.stringify({ id, method, params }));
    setTimeout(function () { /* 超时处理 */ }, timeoutMs);
  });
}
```

### 附带解决的第二个问题：配置无法持久化

排查中发现：**注入脚本运行的"主世界"上下文里没有 `localStorage`**。

用 CDP 枚举执行上下文实测：

| contextId | 名称 | localStorage | 有注入脚本 |
|-----------|------|--------------|-----------|
| 1 | （主世界，`Runtime.evaluate` 默认落在这里） | **undefined** | ✓ |
| 2 | Electron Isolated Context | object | ✗（但共享同一 DOM） |
| 3 | 另一个 frame | object | ✗ |

→ 原来的 `localStorage` 配置层静默降级成内存变量，**重启 Discord 后 API Key 就丢了**。

**解决**：配置改由 Python 侧持久化到 `dt_config.json`，页面通过桥接读写：

```
getConfig  → 读 dt_config.json
setConfig  → 写 dt_config.json
```

好处：重启不丢失、可直接用记事本编辑、也不依赖页面存储能力。

### 顺带修掉的一个定位 bug

`positionBubble()` 在气泡还是 `display:none` 时调用 `getBoundingClientRect()`，
拿到的高度恒为 0，导致气泡定位偏低（压住原文）。

**修复**：先 `display:block` 再测量：

```js
bubbleEl.style.display = 'block';   // 必须先显示，才能量到真实高度
bubbleEl.style.opacity = '0';
positionBubble(targetEl);
void bubbleEl.offsetHeight;
bubbleEl.style.opacity = '1';
```

## 六、可复用的通用结论（给其他项目参考）

1. **Electron 桌面应用不要指望 Chrome 扩展方案**：`--load-extension` 的 content script 在 Electron 里不执行。
2. **CDP 注入是操作 Electron 应用的通用手段**：`--remote-debugging-port` + `--remote-allow-origins=*`，用 `Page.addScriptToEvaluateOnNewDocument` 持久注入。
3. **页面有 CSP 时，页面内 fetch 外部 API 一定失败**：`Page.setBypassCSP` 对已加载文档无效，正确做法是 **`Runtime.addBinding` 桥接到进程外发请求**。
4. **`Runtime.addBinding` 是绕开 CSP 做网络请求的最干净方案**：原生绑定不是网络请求，CSP 管不到；配合 `Runtime.bindingCalled` 事件 + `Runtime.evaluate` 回传即可实现双向通信。
5. **Electron 主世界上下文可能没有 `localStorage`**：不要假设页面存储可用，关键配置放到进程外（文件）更可靠。
6. **`Runtime.evaluate` 未指定 `contextId` 时落在"主世界"**，用 `Runtime.enable` 收集 `executionContextCreated` 事件可以枚举全部上下文来排查。
7. **PyInstaller `--add-data` 必须用绝对路径**（配合 `--specpath` 时相对路径基准会变）。
8. **给 Discord 启动前要清除 `HTTP_PROXY` 等环境变量**，其更新器不读系统代理，环境变量会把它带偏。

# 【重要更新】v2.2 —— 支持机器人卡片消息（Embed / Components V2）

## 一、问题现象

用户反馈：某条机器人发的卡片消息悬停后**完全没反应**，不弹翻译气泡。
（截图内容：Appy 机器人的 "Giveaway Entered / You have successfully entered the giveaway for 100rbx!"）

## 二、根因定位

排查 `findMessageEl()`，它当时只有这几个选择器：

```js
target.closest('[id^="message-content-"]')      // 普通消息文本
target.closest('[class*="messageContent"]')     // 旧版类名
target.closest('li[id^="chat-messages-"]')      // 整条消息兜底
```

问题在于：**卡片消息的内容根本不在 `message-content-*` 里**。
Discord 把非文字内容（附件、卡片、表情回应）放在另一个容器 `[id^="message-accessories-"]` 中。

实测枚举页面容器数量，证实了这一点：

```
[id^="message-content-"]        11
[id^="message-accessories-"]    11
[class*="embedWrapper"]          0   ← 旧版 embed 类名已不存在
[class*="embedFull"]             0
```

继续展开 `message-accessories` 的子树，发现 Discord 已经改用
**Components V2** 卡片体系，类名全部是带哈希的新名字：

```
root id=message-accessories-1553374184061669387  class=container_b7e1cb
  <DIV> container__5e208 isComponentsV2__5e208
    <DIV> container__60fa3 withAccentColor__60fa3        ← 左侧彩色竖条就是它
      <DIV> markup__75297 markdownContainer__48344 ...   ← 文本块在这
      <DIV> markup__75297 markdownContainer__48344 ...
    <DIV> container__1647d                               ← 按钮区
```

**结论：卡片文字在 `[class*="markdownContainer"]` 里，旧版 `embedWrapper` 类名早已废弃。**

## 三、修复：分层选择器策略

把 `findMessageEl()` 改成按优先级逐层降级，兼顾"精确"和"兜底"：

| 优先级 | 选择器 | 用途 |
|---|---|---|
| 1 | `[id^="message-content-"]` | 普通消息（保持原有行为，最高优先级） |
| 2 | `[class*="markdownContainer"]`、`embedDescription/Title/FieldValue/FieldName/AuthorName/FooterText` | 卡片里**鼠标所指的那一段** |
| 3 | `embedFull`、`embedWrapper`、`isComponentsV2`、`withAccentColor` | 整张卡片（悬停在留白/按钮上时） |
| 4 | `[id^="message-accessories-"]` | 附件容器兜底 |
| 5 | `repliedMessage`、`forwardedMessage`、`messageReference` | 回复引用 / 转发预览 |
| 6 | `[class*="messageContent"]` | 旧版类名兜底 |
| 7 | `li[id^="chat-messages-"]` 内查找 | 整条消息兜底 |

同时加了一个 `hasText()` 守卫，避免匹配到空容器。

**设计取舍**：卡片里翻译"鼠标所指的那一段"而不是整张卡片，
因为卡片内部还混着按钮文字、表情回应数、时间戳，整块翻译会很吵。
但悬停在卡片留白处时会降级到整张卡片，保证"怎么悬停都有反应"。

## 五、教训

**Discord 的 DOM 类名是构建时哈希的，且会随版本更换整个体系。**
（`embedWrapper` → `isComponentsV2` 就是一次体系更换）

因此选择器**不能写死单一类名**，必须：
1. 用 `[class*="..."]` 前缀匹配，不用精确类名
2. 分层降级，任何一层失效还有下一层兜底
3. 用户反馈"某类消息不翻译"时，**先去 DOM 里枚举类名**，别凭记忆猜

## 二、会影响翻译速度吗？——不会，第 3 条反而更快

| 改动 | 对速度的影响 | 原因 |
|---|---|---|
| 界面语言 | **零影响** | 纯静态文案，渲染时取一次，不涉及网络 |
| 目标语言 | **零影响** | 只改了 system prompt 里的一个语言名，token 数几乎不变 |
| 同语言不翻译 | **变快** | 本地判断只要 <1ms；命中就完全跳过 API 请求，省掉 1~3 秒和一次费用 |
| 气泡配色/透明度 | **零影响** | 纯 CSS，改的是 `background` 和文字颜色 |

结论：**四项改动都不会拖慢翻译，第 3 项还会明显减少请求次数。**

另外顺手加了个小优化：**"正在翻译…"延迟 350ms 才显示**。
以前是立刻显示，命中缓存时会闪一下；现在缓存命中和极快返回都不闪。

## 三、语言识别是怎么做的

判断"悬停的文本是不是已经是目标语言"，在页面本地完成，**不消耗 API 调用**。

### 第一层：字符集判断（对非拉丁语言，几乎不会错）

| 语言 | 判据 |
|---|---|
| 日语 | 出现平假名 / 片假名（`\u3040-\u30FF`） |
| 韩语 | 谚文（`\uAC00-\uD7AF`）占比 > 30% |
| 中文 | 汉字（`\u4E00-\u9FFF`）占比 > 30%，且无假名 |
| 俄语 | 西里尔字母（`\u0400-\u04FF`）占比 > 30% |
| 阿拉伯语 | `\u0600-\u06FF` 占比 > 30% |
| 泰语 | `\u0E00-\u0E7F` 占比 > 30% |

### 第二层：虚词打分（对拉丁字母语言）

英 / 西 / 法 / 德 / 葡 / 意 / 越 七种语言各配一份虚词表（the/and/is、que/los/una、le/des/est …）。
分词后统计命中数，取最高分：

- 长句（> 4 个词）：命中 ≥ 2 个且占比 ≥ 12%
- 短句（≤ 4 个词）：命中 ≥ 1 个即可

**关键细节：先做变音符号归一化。**
`của→cua`、`más→mas`、`über→uber`、`được→duoc`，
否则带音标的文本永远对不上词表。做法是 `NFD 分解 + 去掉组合记号`，
再单独处理 `đ/Đ`（它不会被 NFD 分解）。

越南语还有个前置判断：出现 `đ ă â ê ô ơ ư` 或 `\u1EA0-\u1EF9` 直接判为越南语，
因为越南语在拉丁字母里特征很明显。

### 第三层：大模型兜底

识别不出来时（太短、纯数字、纯表情）照常发给大模型，prompt 里明确要求
"如果原文已经是目标语言，就原样返回，一个字都不要改"。

页面拿到结果后比对：**译文与原文（去空白、转小写）相同 → 不显示气泡**。
所以任何情况下都不会弹出"和原文一模一样"的气泡。

## 五、测试中揪出的两个真实 bug

这两个都不是新功能引入的，是**测试过程中顺带发现的旧缺陷**，都修了。

### bug 1：脚本被注入到内嵌 iframe，Discord 里的小游戏也冒出悬浮球

**现象**：用户反馈"为什么在我的 Roblox 游戏里面能看到这个翻译助手？"

**排查**：枚举 CDP 执行上下文，结果一目了然：

```
ctx=7  顶层文档  injected=true   ball=true
ctx=8  顶层文档（隔离世界）        ball=true
ctx=9  内嵌 iframe (about:blank)  injected=true   ball=true   ← 问题在这
```

**根因**：`Page.addScriptToEvaluateOnNewDocument` 会把脚本注入到页面里的**每一个 frame**，
不只是主文档。Discord 里内嵌的网页内容（活动、从 Discord 启动的小游戏）也吃到了脚本，
于是里面也建了一个悬浮球。

**修复**：脚本开头加顶层判断，非顶层直接 return：

```js
let isTopFrame = false;
try {
  isTopFrame = (window.top === window.self);
} catch (e) {
  isTopFrame = false;   // 跨域 iframe 访问 window.top 会抛异常
}
if (!isTopFrame) {
  console.log('[DT] 当前处于内嵌框架，跳过界面注入');
  return;
}
```

### bug 2：重启 launcher.exe 后桥接变死，一直提示"翻译服务响应超时"

**现象**：关掉 launcher.exe 再重新打开，Discord 页面没刷新，之后所有翻译都超时。

**排查**：在页面里挂钩 `__dtDispatch`，再调 `__dtNative`：

```
绑定类型      : function
调用 __dtNative: ok
__dtDispatch 记录: []        ← 调用发出去了，但永远没有回传
```

**根因**：`Runtime.addBinding` 装的 `__dtNative` 是个全局属性。
launcher.exe 退出后，属性本身**留在页面里**，但指向的是已关闭的旧 CDP 会话。
此时重启 launcher.exe，因为属性已存在，新的 `addBinding` **不会覆盖它** —— 桥接就死了。

**试过无效的方案**：

| 方案 | 结果 |
|---|---|
| `Runtime.removeBinding` 再 `addBinding` | ✗ 仍然不通 |
| 换一个全新的绑定名 | ✗ 仍然不通（事件到不了新会话） |
| 把新绑定赋值给 `window.__dtNative` | ✗ 属性改不动 |

**有效方案**：先 `delete` 掉残留属性，再 `addBinding`：

```python
self.send('Runtime.evaluate', {
    'expression': 'try{delete window.__dtNative}catch(e){}',
    'returnByValue': True})
self.send('Runtime.addBinding', {'name': '__dtNative'})
```

实测 `delete` 返回 `true`、`typeof` 变成 `undefined`，重新 `addBinding` 后通道**立刻恢复**，
**不需要刷新页面**。所以启动流程里加了这一步 + 一个通道自检：

```python
def ping_bridge(self, timeout=6):
    """页面调用 __dtNative，本程序能否真的收到"""
```

自检不通过时日志会打印「通道自检未通过，请在 Discord 里按 Ctrl+R 刷新页面」。

> 写自检时又踩了同一个坑：`bindingCalled` 事件常常**先于** `evaluate` 的响应到达，
> 被 `send()` 收进了 `self.events` 队列，自检只读 socket 就会误报失败。
> **凡是"发命令后等事件"的代码，都必须先翻自己的事件队列。** 这个坑在 v2.1 已经踩过一次了。

### 顺带修掉的小问题

`find_main_page()` 原来只判断 `'discord.com' in url`，
而 Discord 还会有 `/popout` 弹出窗口（弹出的通话/视频），同样是 `type=page`。
如果 popout 在列表里排前面，脚本就被注入到弹出窗口去了。
改成**优先选 URL 含 `/channels/` 的**，没有才退回任意 discord.com 页面。

## 七、教训（v2.3 新增）

1. **`Page.addScriptToEvaluateOnNewDocument` 会注入所有 frame**，不是只有主文档。
   凡是往页面加 UI 的注入脚本，都要先判断 `window.top === window.self`。

2. **`Runtime.addBinding` 装的是全局属性，launcher 退出后属性会残留在页面里**，
   导致下次启动时新绑定不生效。启动流程里必须先 `delete` 再 `addBinding`，并做通道自检。

3. **"发命令后等事件"的代码，必须先翻自己的事件队列**再读 socket。
   CDP 事件经常先于响应到达 —— 这个坑 v2.1 和 v2.3 各踩了一次。

4. **多窗口场景要挑对 target**。Discord 的 `/popout` 和 `/channels/` 都是 `type=page`，
   只看域名会挑错，必须看路径。

5. **测试脚本本身也会骗人**。这一轮里测试脚本犯过三个错：
   把面板节点 `remove()` 掉（导致页面脚本引用游离节点）、
   `send()` 把事件丢掉、等待时间不够就断言。
   断言失败时，**先怀疑测试脚本，再怀疑产品代码**。
